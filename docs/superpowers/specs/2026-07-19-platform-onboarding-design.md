# Monad RND 외부 플랫폼 온보딩 설계

작성일: 2026-07-19  
상태: 사용자 검토 대기  
선택안: B안 — 공통 관문과 역할별 실행 문서

## 1. 목표

다른 Monad 플랫폼이 이 저장소를 처음 접하더라도 다음 내용을 스스로 판단하고 실행할 수 있게 한다.

1. 이 RND 방식이 자기 서비스에 적합한지 판단한다.
2. Tx1과 Tx2를 하나의 끊기지 않는 서비스 흐름으로 구현한다.
3. 직접 배포 또는 Factory 배포를 안전하게 수행한다.
4. 컨트랙트 주소와 코드를 검증한다.
5. Tx2 실행, permissionless rescue, RPC 장애와 만료를 운영한다.
6. 이 방식이 VRF가 아니라는 보안 한계를 사용자에게 정확히 설명한다.

## 2. 가장 중요한 공통 원칙

모든 온보딩 문서와 사이트의 Integrate 페이지 첫 화면에 다음 원칙을 표시한다.

> Tx1은 난수 요청을 잠그는 단계일 뿐입니다. 난수는 Tx2가 성공해 결과를 온체인에 저장해야 완성됩니다. 플랫폼은 Tx1과 Tx2를 반드시 하나의 제품 흐름으로 연동해야 합니다.

이를 비개발자 관점에서는 다음과 같이 풀어 설명한다.

- Tx1: 결제·참가·상품 재고와 난수 요청을 함께 잠근다.
- 대기: 정해진 미래 블록들이 생성될 때까지 기다린다.
- Tx2: 블록 증거를 제출하고 난수를 확정하여 영구 저장한다.
- 보상: Tx2 성공을 확인한 뒤 확정된 난수로 보상을 계산하고 지급한다.
- 구조 실행: 요청자가 Tx2를 하지 않으면 permissionless 구간부터 누구나 같은 Tx2를 대신 실행할 수 있다.
- 만료: 마지막 증명 가능 블록까지 Tx2가 없으면 난수를 더 이상 만들 수 없으므로 플랫폼의 사전 보상 정책을 적용한다.

금지해야 할 통합 방식도 명확히 적는다.

- Tx1만 호출하고 즉시 보상을 지급하지 않는다.
- 결과를 본 뒤 결제를 취소하거나 요청을 다시 고르게 하지 않는다.
- 프론트엔드 탭이 계속 열려 있을 것이라고 가정하지 않는다.
- “permissionless”를 “자동 실행”이라는 뜻으로 설명하지 않는다.

1. 5분 적합성 판단표

3. 블록 생성자 편향과 가치 상한
4. Tx1→Tx2 전체 수명주기
5. 누가 가스를 내는지와 프로토콜 수수료 0의 의미
6. requester, rescue caller, owner, treasury 역할표
7. 만료와 고객 보상 정책
8. mainnet 사용 전 별도 보안 검토 필요
9. Go/No-Go 체크리스트

3. Tx1에서 결제·자격·재고를 원자적으로 잠그는 wrapper 예제
4. `entryId ↔ requestId ↔ player` 저장 예제
5. wrapper가 requester가 된다는 주의사항
6. wrapper의 Tx2 전달 함수 예제
7. requester 전용 구간과 permissionless rescue 구간
8. 세 개의 raw block header 수집과 Tx2 제출
9. 확정된 난수 조회와 편향 없는 범위 추첨
10. 중복 Tx1 방지와 업무 단위 idempotency key
11. 브라우저 데모와 실제 프로덕션 SDK의 차이

핵심 예제는 다음 두 함수를 한 쌍으로 보여준다.

- `openEntry(...)`: 결제와 Tx1을 하나의 트랜잭션으로 실행
- `finalizeEntry(...)`: wrapper를 통해 Tx2를 실행하고 보상 정산

## 4. 사이트 변경

현재 사이트에 다음 변경을 적용한다.

1. 상단 메뉴에 `Integrate`를 추가한다.
2. `/integrate` 페이지에서 네 문서의 읽는 순서를 안내한다.
3. 첫 화면에 Tx1과 Tx2가 모두 필요하다는 경고를 표시한다.
4. 데모가 Monad Testnet 참고 구현이며 프로덕션 SDK가 아님을 표시한다.
5. `speed-up/cancel을 항상 추적한다`는 보편적 표현을 제거한다.
6. 컨트랙트 주소, runtime hash, owner/config를 각각 확인해야 한다고 안내한다.
7. 외부 사용자가 접근할 수 있도록 승인 후 사이트를 공개한다.

사이트에는 전체 운영 문서를 중복 복사하지 않고, 핵심 흐름과 저장소 문서 링크를 제공한다. 문서의 단일 진실 공급원은 저장소의 Markdown 파일로 둔다.

## 5. README 변경

README 첫 부분에 다음 순서의 문서 지도를 추가한다.

1. 도입 판단
2. 개발 연동

## 6. 보안 및 운영 경계

문서 전반에 다음 사실을 반복해서 일관되게 표시한다.

- 프로토콜 이용료는 0이지만 각 트랜잭션 호출자는 가스를 낸다.
- Tx2는 누군가 호출해야 하며 자동으로 발생하지 않는다.
- permissionless rescue는 결과 조작 권한이 아니라 동일한 결과를 대신 저장하는 권한이다.
- 플랫폼 wrapper가 Tx1을 호출하면 requester는 wrapper다.
- 요청 가격 0과 `maxPending`만으로 Sybil 공격을 막을 수 없다.
- 블록 생성자의 비용성 편향 가능성이 남으므로 고가치 상품은 외부 VRF 또는 threshold randomness를 사용한다.
- EIP-2935 증명 범위를 넘기면 난수를 복구할 수 없다.
- 공개 RPC에는 프로덕션 SLA가 없다.
- 현재 브라우저 데모의 localStorage와 Web Locks는 프로덕션 원장이 아니다.
- 현재 검토 결과는 독립적인 전문 보안 감사나 버그바운티를 대체하지 않는다.

## 7. 언어와 독자 수준

- 외부 Monad 빌더가 바로 사용할 수 있도록 실행 문서는 영어를 기본으로 한다.
- 각 문서 첫 부분에는 비개발자도 이해할 수 있는 짧은 요약을 둔다.
- 코드 예제는 설명→코드→확인 결과 순서로 제시한다.
- 전문 용어는 처음 등장할 때 쉬운 말로 정의한다.

## 8. 검증 기준

구현이 완료됐다고 판단하려면 다음을 모두 만족해야 한다.

1. 네 문서가 서로 모순 없이 Tx1과 Tx2의 연결을 설명한다.
2. wrapper 예제에 Tx1과 Tx2 전달 함수가 모두 존재한다.
3. 사용자가 Tx1만 구현하고도 완료됐다고 오해할 문장이 없다.
4. requester 전용·permissionless rescue·만료 경계가 컨트랙트 상수와 일치한다.
5. 배포 명령과 runtime hash가 현재 아티팩트와 일치한다.
6. Monad RPC 요구사항이 실제 공식 문서 및 실연결 검사와 일치한다.
7. 사이트와 README에서 프로덕션 SDK가 아닌 데모라는 범위가 일치한다.
8. 모든 Forge 테스트, 클라이언트 테스트, 빌드, 린트가 통과한다.
9. 프로덕션 사이트에서 `/integrate`, 데모, 아티팩트를 직접 확인한다.
10. 마지막 독립 재검토에서 Critical 또는 Important 미해결 문서 오류가 없다.

## 9. 구현 범위에서 제외하는 것

이번 온보딩 문서 작업에는 다음을 포함하지 않는다.

- 외부 VRF 또는 threshold randomness 구현
- 중앙 운영 서버 또는 유료 keeper 서비스 구축
- mainnet 안전성 보증
- 독립 보안 업체의 감사
- 범용 npm SDK 발행
- 다른 플랫폼의 개별 고객 보상 정책 결정

이 항목들은 문서에서 필요한 후속 작업으로 구분한다.
